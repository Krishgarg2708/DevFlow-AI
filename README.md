## Phase 3 — Frontend Foundation: verification notes

Same approach as Phase 2: actually ran `npm install` / `npm run build` instead of trusting the scaffold, and fixed what broke:

1. **Missing Vite env types** — `import.meta.env.VITE_API_URL` failed `tsc` with "Property 'env' does not exist on type 'ImportMeta'". Added `src/vite-env.d.ts`.
2. **`@/*` path alias didn't actually work** — it was declared in `tsconfig.json` but TypeScript's `paths` config doesn't affect Vite's bundler; every `@/`-prefixed import would have failed at runtime despite `tsc` passing in isolation. Added `resolve.alias` to `vite.config.ts`.
3. **Light/dark mode was fake** — the spec (section 19) requires both, but the app was hardcoded to a dark palette with no toggle and no light variants anywhere. Added a real `ThemeProvider` (localStorage + system-preference detection, no flash-of-wrong-theme via an inline pre-paint script in `index.html`), a toggle in the topbar, and light/dark Tailwind variants across every component.
4. While doing (3) by find-and-replace across ~10 files, introduced and then caught two of my own bugs: cascading duplicate classes (`dark:text-slate-500 dark:text-slate-400 dark:text-slate-500...`) from running overlapping regex passes, and a couple of hover states that lost their `hover:` prefix on the dark variant (which would've made a hover-only color permanent in dark mode). Both found by grep-auditing the diff, not caught by the build — `tsc`/Vite don't type-check Tailwind class strings, so this class of bug is invisible to the compiler. Fixed by hand and re-verified with a targeted grep sweep, not another blind regex pass.

Verified end-to-end from the actual packaged zip (not just the working copy): extracted fresh, `pytest` (backend, 10/10) and `npm run build` (frontend) both re-run successfully from the extracted files.

## Phase 2 — Backend Foundation: verification notes

Phase 2's own spec said "test everything" — that was previously unmet (tests existed but nothing had run against a real database). This pass actually did it: installed Postgres, generated the Alembic migration via `--autogenerate` against live models, applied it, seeded it, ran the app, and hit real endpoints with curl. That surfaced and fixed four genuine bugs the scaffold had:

1. **passlib/bcrypt incompatibility** — `bcrypt>=4.1` breaks passlib 1.7.4's backend detection. Pinned `bcrypt==4.0.1`.
2. **Missing `email-validator`** — `EmailStr` fields crashed FastAPI's schema generation on startup. Added `email-validator` to requirements.
3. **UUID serialization bug (the big one)** — every `*Out` Pydantic schema typed id/foreign-key fields as `str`, but Pydantic v2 does not auto-coerce a `UUID` object to `str` even with `from_attributes=True`. Every endpoint returning a list (`/projects`, `/issues`, `/tasks`, `/notifications`, `/github/repositories`) was one request away from a `ResponseValidationError` 500. Fixed with a shared `ORMModel` base (`app/schemas/base.py`) that coerces UUIDs before validation, applied to all six `Out` schemas.
4. **AI provider errors leaked as opaque 500s** — an Anthropic SDK exception (bad key, rate limit, etc.) wasn't caught, so it surfaced as a generic `INTERNAL_ERROR` instead of a clean, debuggable error. Added `_complete_or_raise` in `ai_service.py` to convert `anthropic.APIError` into a proper `AppError` (502, `AI_PROVIDER_ERROR`).

Also fixed a test-suite bug: the async SQLAlchemy engine binds to the event loop active when it's imported, but pytest-asyncio's default per-test loop scope creates a fresh loop each test, which broke the pooled connections after the first test (`RuntimeError: Event loop is closed`). Session-scoped the test event loop to match.

Alembic migration `11cecb550d8a_initial_schema.py` is real, autogenerated, and verified to apply cleanly to a fresh database (dropped and rebuilt from scratch as part of this verification — 20 tables + `alembic_version`, confirmed via `psql`). `app/tests/` now has 10 tests, including integration tests that pin the two response-serialization bugs so they can't regress, all passing against a live Postgres instance rather than mocks.

## Status

**Working end-to-end (real code, runs with `docker compose up`):**
- Full DB schema as SQLAlchemy models (all 20 tables) + Alembic wired up
- JWT auth: register, login, refresh-token rotation, logout, bcrypt hashing
- RBAC dependency (`require_role`) enforced server-side, not just hidden UI
- Projects + Issues CRUD API with membership-based authorization
- AI abstraction layer (`AIProvider` protocol) with a working Anthropic implementation, used by real `/api/ai/code-review`, `/api/ai/issue-generator`, `/api/ai/assistant` endpoints, with token/cost tracking in `ai_usage`
- **GitHub OAuth**: full code-exchange flow, encrypted token storage (Fernet), repo listing, repo import with initial PR sync (`app/services/github_service.py`, `app/integrations/github_client.py`)
- **GitHub webhooks**: HMAC-verified endpoint stores every event, then dispatches to a real Celery handler that updates `pull_requests`/`issues` and fans out `notifications` to project members (`app/workers/github_tasks.py`) — covers `pull_request`, `issues`, and `push` events
- Notifications: table + list/mark-read/**mark-all-read** endpoints (fixed a serialization bug — the endpoint was returning raw ORM rows), **frontend bell with 15s polling, unread badge, click-to-read, click-outside-to-close**
- **Kanban board**: full Task CRUD API with per-column position ordering, frontend board with native HTML5 drag-and-drop across all 5 columns, optimistic updates (add/move/delete) that reconcile with the server on failure, inline "add task" per column
- React + TS frontend: routing, protected routes, login/register wired to the real API, dashboard shell + sidebar + topbar, GitHub connect button → OAuth callback → repository list/import UI, Tailwind dark theme
- Docker Compose (postgres, redis, backend, worker, frontend) + GitHub Actions CI (lint, test, build both images)
- Demo seed script (`scripts/seed.py`) creating admin/lead/developer users + sample project/issues
- Unit tests for webhook signature verification

**Deliberately stubbed — architecture is in place, logic is not:**
- PR dashboard UI, analytics charts UI, Projects list/create UI (Kanban board currently takes a project id straight from the URL rather than a project picker)
- WebSocket notification delivery (the bell works via polling; a real-time push would replace the 15s interval)
- Analytics aggregation job (`compute_analytics_snapshot` — still `NotImplementedError`)
- Rate limiting, Redis caching of AI responses, full audit-log coverage
- Commit-level sync (client method exists in `github_client.py`, not yet called by the import flow)

Honest reason: these each need nontrivial UI state or a scheduling layer (celery beat) that's a real multi-day build on top of what's here, not something worth faking with placeholder logic that would need to be thrown away.

See `docs/ARCHITECTURE.md`, `docs/DATABASE_SCHEMA.md`, `docs/API_ROUTES.md` for the full design all of the above follows.

## Quickstart
```bash
cp .env.example .env   # fill in JWT secrets + AI_API_KEY at minimum
docker compose up --build
# in another shell, seed demo data:
docker compose exec backend python -m scripts.seed
```
Frontend: http://localhost:5173 · API docs: http://localhost:8000/docs

## Stack
- **Frontend**: React, TypeScript, Vite, Tailwind, shadcn/ui, TanStack Query, React Hook Form + Zod, Recharts
- **Backend**: FastAPI, SQLAlchemy, Alembic, PostgreSQL, Redis, Celery, WebSockets
- **AI**: provider-agnostic layer (default: Anthropic Claude)
- **Infra**: Docker, Docker Compose, GitHub Actions CI/CD
